## Problem Definition & Problem Statement
- Add an AI-powered capability to the Task Management application using the OpenAI or Gemini API.
- The feature must serve a meaningful workflow purpose: automatically drafting task descriptions and suggesting priority levels based on task titles.
- The AI API key must be stored and accessed exclusively on the backend via `.env`, never exposed to client-side bundles or browser DevTools.
- Handle third-party API errors gracefully: if an AI call fails, times out, or quota runs out, the core application must remain completely stable.
- Display the AI response meaningfully within an editable interface for human oversight, rather than dumping raw JSON.

## Key Questions & Analysis

### 1. Why must the AI API key be called from the backend rather than directly from the React frontend?
Client-side web applications execute directly inside the user's browser. If an API key is stored in frontend variables or used in browser `fetch()` calls, it is visibly exposed in the browser's Network tab and embedded inside the compiled JavaScript bundle. Anyone inspecting DevTools can extract the key and abuse the associated account, causing massive billing charges or quota exhaustion. 

Calling the AI API from an Express backend ensures the key is stored strictly on the server in `.env`. The frontend only communicates with our private `/api/ai/generate-description` endpoint, keeping credentials 100% secure.

### 2. What does 'graceful degradation' mean in this context, and why does it matter for a feature that depends on a third-party service outside your control?
Graceful degradation is an architectural resilience pattern where an application continues providing core utility even when secondary external dependencies encounter failures, rate limits, or outages. 

Because third-party AI APIs can experience downtime, network latency, or quota exhaustion outside our control, our backend wraps external AI requests in robust `try...catch` blocks. If an API call fails or an invalid key is provided, the backend falls back to an internal heuristic generator that provides a relevant task outline with `{ fallback: true }`. The core task management workflow continues running smoothly without crashing or blocking the user.

### 3. What are the privacy and governance implications of sending task data to an external AI API, and what kind of data should never be sent this way?
Transmitting information to public AI services transfers data across third-party servers where it may be subject to external data retention policies or used for model fine-tuning unless strict enterprise zero-retention agreements are active.

From a data privacy and regulatory compliance standpoint (e.g., GDPR, HIPAA), the following categories of data must **never** be sent to external AI APIs:
- Passwords, cryptographic keys, and database credentials.
- Personally Identifiable Information (PII) such as personal phone numbers, addresses, and government identification numbers.
- Proprietary source code, financial records, and confidential business documents.
- Sensitive health or medical records.

## Supplementary Problems

### 1. Frontend Loading State
The user interface implements an asynchronous loading state. When "Generate AI" is triggered, the button disables and displays `"🤖 Thinking..."`, preventing duplicate requests during model inference.

### 2. Request Rate Limiting
A server-side rate limiter enforces a cooldown period per client to prevent spamming the endpoint and avoid accidental quota exhaustion.

### 3. Responsible AI Disclaimer & Human-in-the-Loop
A visible disclaimer notifies users that suggestions are generated by an AI assistant. The generated description is injected into an editable textarea, ensuring the user retains full agency to review, edit, or reject model suggestions before saving the task.
